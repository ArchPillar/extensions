# 07 — Number Formatting

## Overview

The number engine renders `{n, number, style}` inside a MessageFormat template and the standalone
`ToLocalizedString` extensions from embedded CLDR-48 pattern, compact, and currency data — ICU-78-faithful
by construction — rather than delegating to `System.Globalization`, which exposes no CLDR plural rules,
no `::`-skeletons, and no CLDR currency display data. `System.Globalization` still supplies the per-culture
atoms the engine composes around: group and decimal separators, group sizes, the negative sign, and the
percent sign. For consumer-facing usage — named styles, skeletons, currency widths, compact notation, and
`ToLocalizedString` — see [`../features.md`](../features.md#number-currency--compact-formatting). This page
documents the machinery underneath.

## The style slot

A `{name, number, style}` placeholder's `style` is resolved by `NumberFormatting.Resolve`
(`src/Localization.MessageFormat/Internal/NumberFormatting.cs`) into one of two shapes, both producing the
same internal record:

```csharp
internal sealed record NumberFormatSpec(
    NumberUnit Unit,
    string? CurrencyCode,
    int? MinFractionDigits,
    int? MaxFractionDigits,
    bool Grouping,
    NumberNotation Notation,
    CurrencyWidth Width = CurrencyWidth.Short);
```

- **A named style** — `integer`, `currency`, or `percent` — a fixed `NumberFormatSpec` with no further
  options.
- **An ICU `::`-skeleton** — a space-separated list of stems, parsed by `NumberSkeleton.Parse`
  (`src/Localization.MessageFormat/Internal/NumberSkeleton.cs`) into the same `NumberFormatSpec`.

The slot is **ICU-only**: a .NET custom format string (`"N2"`, `"C"`) is never accepted, because it would
mean two competing style grammars for the same placeholder. An unrecognized named style or an unsupported
skeleton stem throws `MessageFormatException` at **position `-1`** — the exception's position field is
meaningful for template-parse errors (a character offset into the message text) but a style is resolved
after parsing, against no single character, so `-1` marks "not a parse-position error" rather than
guessing a location. This is a **fail-fast** boundary: an unknown stem is a template bug, not a runtime
condition to tolerate.

`NumberSkeleton.Parse` accepts exactly this subset (the authoritative list is the stem `if`/`else if` chain
in `NumberSkeleton.cs`; anything else falls to the final `else` and throws):

| Stem | Effect |
|------|--------|
| `currency/<ISO>` | Currency, explicit ISO code — **does not follow the UI language** |
| `unit-width-short` / `-narrow` / `-iso-code` / `-full-name` | Currency width: symbol / narrow / ISO code / full plural name |
| `.00` / `.##` / `.0#` | Fixed / optional / mixed fraction digits |
| `percent` | Percent |
| `integer` (`precision-integer`) | Integer, no fraction |
| `group-off` / `group-auto` | Grouping off / default |
| `compact-short` (`K`) / `compact-long` (`KK`) | Compact notation (stems combine, e.g. `::compact-short currency/USD`) |

Stems combine (`::compact-short currency/USD`), and `NumberSkeleton.Parse` cross-validates the
combination: compact notation rejects an explicit fraction override and rejects `percent`; a currency
width other than `short` rejects combining with compact notation. Each of these is also a fail-fast
`MessageFormatException`, not a silently-ignored stem.

## CLDR data and the pinned resource

Three independent CLDR datasets back the engine, each generated — never hand-edited — from pinned source
JSON under `eng/cldr/`, and each recording its own `CldrVersion` constant:

- **`CldrNumberPatterns.g.cs`** — the standard decimal/percent/currency patterns per locale (a
  `CldrNumberPatternSet` per distinct pattern triple, deduplicated and referenced by locale — see the
  `_set0`, `_set1`, … pool in the file). Generated by `eng/cldr/generate-number-patterns.cs` from
  `eng/cldr/numbers.json`, which `eng/cldr/extract-numbers.cs` produces from the CLDR `cldr-numbers-full`
  data.
- **`CldrCompactData.g.cs`** — the short/long decimal and short-currency compact bucket sets (magnitude,
  per-plural-category pattern, and any explicit-value variant), one `CompactLocaleData` per locale.
  Generated by `eng/cldr/generate-compact-data.cs` from `eng/cldr/compact.json`.
- **`CldrCurrencyData.g.cs` + the embedded `CldrCurrencyData.bin`** — the per-locale currency symbol,
  narrow symbol, plural display names, `unitPattern-count-*`, and `currencySpacing`, plus the per-currency
  minor-unit (fraction-digit) overrides. Unlike the other two datasets, this one is not emitted as C#
  literals: it is too large (every currency in every CLDR locale) to inline as source without bloating the
  assembly, so it ships as a **compressed embedded resource** instead. `CldrCurrencyData.g.cs` is just the
  tiny pin (`CldrVersion`, `ResourceName`); the data itself lives in `CldrCurrencyData.bin`.

The currency resource's format, built by `eng/cldr/generate-currency-data.cs`:

- **Delta-encoded against the locale fallback chain.** Only entries that differ from their resolved
  parent are emitted — a locale inherits everything it does not override. The chain is
  **locale → language → root**, walking straight to the base language on the **first dash**
  (`zh-Hant-HK` → `zh` → `root`, not the segment-wise `zh-Hant` → `zh`). `CurrencyDisplay.Chain` walks it
  for currency-entry lookups (calling the single-locale `CurrencyData.TryEntry` once per step) and
  `CurrencyData.ResolveMeta` walks an equivalent chain for the pattern/spacing lookup
  (`src/Localization.MessageFormat/Internal/CurrencyDisplay.cs`, `CurrencyData.cs`). A source comment on
  `CurrencyDisplay.Chain` flags it as load-bearing precisely because the delta baselines were computed
  against this exact walk — a segment-wise "fix" would resolve three-part locales against the wrong
  baseline.
- **Deflate-compressed.** The resource is a tab/newline-delimited text stream (record kinds `V`/`R`/`K`/`P`/
  `L`/`C`, one per line — version, minor-unit overrides, spacing pool, pattern pool, per-locale metadata,
  per-currency entries) compressed with `DeflateStream`, which keeps the shipped resource well under 1 MB.
- **A BCL-only, lazy loader.** `CurrencyData.Load` (`src/Localization.MessageFormat/Internal/CurrencyData.cs`)
  reads the resource through `DeflateStream` + `StreamReader`, splitting each line on `\t`, behind a
  `Lazy<Model>` so the decompress-and-parse cost is paid once, only if currency formatting is ever used.
  No third-party package, no reflection beyond `Assembly.GetManifestResourceStream`, no runtime XML/CLDR
  parsing — the same AOT/trim-safe posture as the rest of the assembly.

All three generators are .NET file-based apps under `eng/cldr/`, consuming pinned JSON checked into the
same directory. The data is pinned at **CLDR 48**; bumping the version means re-fetching the pinned JSON
against the new release and regenerating all four `.g.cs`/`.bin` artifacts, then re-running the parity
suite — never hand-editing a generated file:

```bash
dotnet run eng/cldr/extract-numbers.cs -- 48.2.0
dotnet run eng/cldr/extract-currency-fractions.cs -- 48.2.0
dotnet run eng/cldr/generate-number-patterns.cs
dotnet run eng/cldr/generate-compact-data.cs
dotnet run eng/cldr/generate-currency-data.cs
```

## Currency display widths

The four `unit-width-*` skeleton stems select which of four CLDR currency representations
`CurrencyDisplay` (`src/Localization.MessageFormat/Internal/CurrencyDisplay.cs`) resolves:

| Width | Source |
|-------|--------|
| `unit-width-short` (default) | The locale's currency **symbol** (`CurrencyEntry.Symbol`), e.g. `$`, `US$`. |
| `unit-width-narrow` | The locale's **narrow symbol** (`CurrencyEntry.Narrow`), falling back to the short symbol when the locale has none. |
| `unit-width-iso-code` | The bare ISO code, upper-invariant — no locale lookup. |
| `unit-width-full-name` | The CLDR plural **display name** (`CurrencyEntry.Names`), keyed by CLDR plural count, composed into the locale's `unitPattern-count-<plural>` around the rendered number — routed through `CurrencyNameRenderer`, a distinct path from the symbol/pattern (`¤`) composition since it carries no symbol and no `currencySpacing`. |

Symbol and narrow-symbol lookups walk the same locale → language → root chain as the data resource.
`currencySpacing` applies only to the symbol/code forms (short, narrow, iso-code): CLDR defines it as a
join rule inserted **at the boundary between an alphabetic/symbol glyph and an adjacent digit**, not a
fixed separator — `PatternRenderer.NeedsSpacing` (`src/Localization.MessageFormat/Internal/PatternRenderer.cs`)
checks the Unicode category of the glyph's number-facing edge (not a Symbol, not a Separator) against the
number's edge (a digit) before inserting the pattern's spacing token. That token is CLDR data, not a
hardcoded character — `CurrencyDisplay.Spacing` reads it from the resource, and it is almost always
U+00A0 (non-breaking space).

> `USD 1,234.56` (`unit-width-iso-code`, en-US) inserts a space between `USD` and `1` — the space is a
> non-breaking space (U+00A0) carried by CLDR's `currencySpacing` data, not a literal space in the pattern.

## Compact notation

`CompactFormatter` (`src/Localization.MessageFormat/Internal/CompactFormatter.cs`) implements TR35 compact
("short"/"long") notation:

1. **Bucket selection.** `CldrCompactData` stores ascending magnitude buckets (1000, 10 000, … up to
   10^14) per locale/notation; `SelectBucket` finds the greatest bucket whose magnitude is at most the
   value, or reports "below the smallest bucket" (plain render).
2. **Divisor + rounding.** The bucket's divisor is `magnitude / 10^(zeroCount - 1)`, where `zeroCount` is
   the number of `0` characters in the bucket's pattern — CLDR's convention that the zero run encodes how
   many significant digits are already shown at that magnitude. A magnitude-1000 bucket with pattern `0K`
   (one zero) divides by 1000 (`1234` → `1.2K`); a magnitude-10000 bucket with pattern `00K` (two zeros)
   *also* divides by 1000 (`12345` → `12.345` → `12K`) — the divisor stays constant across a suffix group
   while the zero count absorbs the extra integer digit. The scaled value is rounded to 0 or 1 fraction
   digit (ECMA-402/`Intl.NumberFormat` compact precision: one fraction digit below 10, none at or above).
3. **Round-and-re-bucket ("carry").** Rounding can push a value into the next magnitude (`999,900` → `1M`,
   not `1000K`); `ResolveCarry` re-checks the rounded value against the next bucket's magnitude and advances
   one bucket when it crosses.
4. **Plural + explicit-value selection.** The rounded, scaled value's plural category (via
   `PluralRules.Cardinal`, computed on the *displayed* digits) selects among the bucket's per-category
   patterns. A CLDR **explicit-value** variant — a pattern tied to one exact compacted value, e.g. French
   `1` → `"mille"` — wins ahead of the category match when the rounded value equals it exactly; a negative
   value does not take the literal (`-1000` → `"-1 millier"`, not `"-mille"`), since French's literal has no
   sign slot.
5. **Currency-compact.** Currency compact notation always uses the CLDR *short*-currency bucket set (CLDR
   defines no long-currency compact form); when the currency symbol is alphabetic at the digit boundary
   (an ISO-code fallback like `USD`, or a letter symbol like `kr`), the `alphaNextToNumber` bucket variant
   is preferred when the locale has one, matching CLDR's own disambiguation between a glyph and a
   letter-symbol sitting against the number.

A **sentinel bucket** — a CLDR "no-compact" magnitude whose `other`-category pattern is the bare literal
`"0"` (e.g. German short-decimal below a million) — and a value below the smallest real bucket both render
through the **standard** pattern instead, with the compact engine's own 0/1 fraction precision and
ECMA-402 "min2" grouping (group only when the integer part is at least two digits past the primary group
size, so `1234` stays ungrouped but `12345` groups).

## Precision and plurals (MF-8)

The number engine and the plural resolver share one rule, [MF-8](04-message-format-and-plurals.md): **the
displayed digits drive both `#` rendering and plural-category selection.** `NumberFormatting.VisibleFractionDigits`
computes the fraction-digit count the default `#,##0.###` display would actually show for a value (rounded
to three places, trailing zeros trimmed); that same digit count is what `PluralRules.Operands` uses to
compute the `v`/`f` operands the CLDR plural rule evaluates. The consequence: `1.0m` renders as `1` and
selects the category for `1`, not for a value with one visible fraction digit — rendering and selection
never disagree. `CompactFormatter.VisibleFraction` and `CurrencyNameRenderer.Render` apply the identical
principle to their own rounded/scaled values, so a compact render (`1.2M` → category from the *displayed*
`1.2`) and a full-name currency render (`JPY 1` → `v=0` → `"one"`; `USD 1` → `"1.00"` → `v=2` → `"other"`)
select consistently with what a reader sees. See
[`04-message-format-and-plurals.md`](04-message-format-and-plurals.md) for the plural/operand model this
plugs into.

## Parity and the oracle

Correctness for this engine is not asserted against hand-written expectations: every concrete rendered
value in the parity suite is derived byte-for-byte from **ICU 78 / CLDR 48** — the same CLDR release the
embedded data is pinned to — via the C# P/Invoke oracle at `eng/oracle/icu-format.cs`. The oracle loads
ICU's `unumf_*` skeleton formatter (the identical `::`-grammar this engine implements) against a
dev-only native ICU runtime fetched by `eng/oracle/fetch-icu.cs`, and formats `(locale, skeleton, value)`
triples on demand or in batch over stdin; it is never shipped with the library. Parity is asserted by:

- `tests/Localization.MessageFormat.Tests/CurrencyDisplayParityTests.cs` — the four currency widths across
  multiple locales and currencies (prefix/suffix symbols, alphabetic disambiguation, narrow-symbol
  fallback, 0- and 3-minor-unit currencies, negatives, plural categories).
- `tests/Localization.MessageFormat.Tests/CldrParityTests.cs` — standard decimal/percent/currency
  composition, including the locale-specific spacing characters (NBSP, NNBSP) asserted exactly.
- `tests/Localization.MessageFormat.Tests/CompactNotationTests.cs` — short/long decimal and currency
  compact notation, including the round-and-re-bucket carry and explicit-value literals.

Two behaviors are intentionally out of scope for this parity sweep — verified not to affect the covered
cases, and not part of the current spec: Arabic-Indic digit shaping (the engine always renders Latin
digits) and `minimumGroupingDigits` suppression (the engine always groups once grouping is on). Both are
documented as deliberate omissions at the top of `CurrencyDisplayParityTests.cs`, not silent gaps.
